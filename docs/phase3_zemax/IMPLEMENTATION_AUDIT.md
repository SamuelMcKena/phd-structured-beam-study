# Phase 3A implementation audit

This audit records the existing repository conventions that the integration must preserve.

## Existing field representations

- Scalar propagation uses complex two-dimensional arrays on explicit Cartesian grids.
- `vbb_study.vector_field.VectorField` is the canonical sampled vector container with `Ex`, `Ey`, `Ez`, `wavelength_m`, medium index and grid metadata.
- `vbb_study.equations.vector_debye.VectorFieldPlane` is the independent three-component focal-plane reference used by Phase 2C.

## Units and grids

- Python-side physical contracts use SI metres and `wavelength_m`.
- G0/B0/V1/V3 Phase 2A/2C uses the accepted half-pixel-centred Cartesian grid. H1 has a separate accepted integer-centred convention and is not part of this first Zemax vortex-report integration.
- A Zemax model may use another display/lens unit; Phase 3 converts it explicitly before comparison and refuses unknown units.

## Canonical solvers

- Scalar FFT/ASM remains the broad morphology screening route.
- Vector Debye/Richards-Wolf remains the quantitative focal/vector reference where claim governance requires it.
- Vector spectral Fresnel remains the component/high-angle interface reference.
- `zemax_pop` is therefore a `validation_backend`, not a canonical objective/interface solver.

## Canonical reference fields used by Phase 3

Phase 3 does not implement another Bessel simulator. `python_reference.py` calls the existing `run_phase2c_benchmark` and adapts its `objective_cases[case].vector` into the Phase 3 `FieldPlane` contract. The underlying G0/B0/V1/V3 pupil fields are generated by Phase 2C from the accepted Phase 2A `_scalar_seed` fixed-bench route.

## Immutable evidence

Accepted Phase 1/1R/2A/2B/2C outputs and the report freeze are not regenerated or overwritten. Phase 3 outputs live only under `outputs/validation/phase3_zemax/` (and any future dedicated Phase 3 figure namespace). The source `.ZOS`/`.ZMX` prescription is also never edited in place: it is hashed and copied to a work area first.

## Claim boundary

Software/API success, prescription-dependent POP agreement, physical cross-validation and experimental validation remain distinct. Traditional ZBF transverse-field exchange cannot establish `Ez` agreement; the Python vector route remains authoritative for longitudinal-field claims.
